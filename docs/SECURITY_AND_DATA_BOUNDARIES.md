# Security and Data Boundaries

## 1. Document Status

- **Application implementation:** Not started
- **Security baseline:** Approved for all milestones
- **Last updated:** 2026-08-05

This document defines mandatory trust, authorization, privacy, and data-minimization rules for the deterministic platform and both agent flows.

## 2. Security Objectives

The system must:

- isolate company data;
- keep Java as the authorization and business-policy boundary;
- prevent agents from receiving raw financial files or unrestricted production access;
- minimize data sent to external LLMs;
- constrain tools by identity, tenant, incident, schema, and purpose;
- preserve human control over repair, merge, and deployment;
- treat uploaded content and model output as untrusted;
- produce auditable but sanitized traces;
- use only synthetic financial data in the portfolio demonstration.

## 3. Trust Model

```text
Browser input                  Untrusted
Uploaded document content     Untrusted
External integration response Untrusted
Python agent orchestration    Not a security boundary
External LLM                  Untrusted
Model output                  Proposal only
Java backend                  Authorization and policy boundary
PostgreSQL constraints        Consistency boundary
Human approver/reviewer       Required control for material changes
CI/CD                         Deployment authority under normal controls
```

No request becomes trusted merely because it was generated by an internal service or an LLM.

## 4. Data Classification

### 4.1 Restricted Data

Must not be sent to an external LLM or included in public fixtures:

- raw financial files;
- financial row values and amounts;
- bank accounts;
- personal identifiers;
- real company names and registration numbers;
- credentials, tokens, private keys, and connection strings;
- complete production logs;
- database dumps;
- session identifiers;
- proprietary customer integration specifications;
- production source files containing secrets.

### 4.2 Sanitized Operational Data

May be exposed through authorized tools when minimized:

- opaque incident and job identifiers;
- integration type;
- parser type and version;
- normalized error code;
- processing stage;
- redacted error trace;
- structural file profile;
- counts, data types, header names or approved header hashes;
- reporting-year count and requested-year presence;
- known warning codes;
- approved known issue summaries;
- synthetic reproduction metadata;
- recent deployment identifiers and non-secret summaries.

### 4.3 Synthetic Data

Synthetic files may be committed when they:

- contain invented values;
- do not reproduce real company or person identifiers;
- do not copy customer rows;
- are documented as synthetic;
- are limited to the structure needed for tests and demos.

### 4.4 Public Documentation Data

Architecture, tool names, synthetic examples, and generic error codes may be public when they reveal no secret, customer, or proprietary implementation detail.

## 5. Tenant Isolation

### 5.1 Core Rule

Every company-scoped operation is authorized in Java.

The backend must not rely on:

- frontend visibility;
- client-provided roles;
- possession of a document, job, incident, or company identifier;
- Python service identity alone;
- model claims about permission.

### 5.2 Authorization Sequence

```text
1. Authenticate user or service identity.
2. Resolve the requested resource server-side.
3. Determine the owning company.
4. Verify membership or scoped service permission.
5. Apply role or action policy.
6. Execute the use case.
7. Record security-relevant audit data.
```

### 5.3 Negative Tests

Required tests include:

- user A cannot read company B;
- user A cannot upload to company B;
- user A cannot read company B's document, job, incident, or recommendation;
- guessed identifiers do not bypass authorization;
- Python cannot request an incident outside its authorized run scope;
- a tool call with a mismatched company and incident is rejected;
- authorization remains enforced after retries and asynchronous delivery.

## 6. Browser Authentication

Version 0.1 uses server-side Spring Security sessions.

Requirements:

- adaptive password hashing;
- HTTP-only session cookie;
- `Secure` in HTTPS environments;
- deliberate `SameSite` policy;
- CSRF protection for state-changing browser requests;
- session invalidation on logout;
- no session identifiers in logs;
- bounded session lifetime;
- safe local and production CORS/cookie configuration.

Shared sessions through Redis are considered only when multiple backend instances create a real requirement.

## 7. Service-to-Service Security

The Python service uses a dedicated service identity.

Requirements:

- credentials stored outside Git;
- short-lived or rotatable credentials where practical;
- transport protection;
- scoped permissions by tool or capability;
- run and incident context attached to calls;
- replay and idempotency protection for state-changing calls;
- rate and timeout limits;
- audit of service identity and tool result.

A valid service credential does not authorize arbitrary companies, incidents, or tools.

## 8. MCP Tool Boundary

### 8.1 Tool Design

Every Spring AI MCP tool must be:

- narrow;
- typed;
- schema-validated;
- authorized;
- company- and incident-scoped;
- size-limited;
- redacted;
- audited;
- deterministic where it makes a business decision.

### 8.2 Forbidden General-Purpose Tools

Do not expose:

```text
execute_arbitrary_sql
read_any_production_file
run_arbitrary_shell_command
access_database_dump
read_all_logs
change_financial_data
change_tax_rules
push_to_main
merge_pull_request
deploy_application
read_production_secrets
```

### 8.3 State-Changing Tools

Tools such as ticket creation, support recommendation creation, escalation, approval request, or retry request require:

- explicit service permission;
- idempotency key;
- current-state validation;
- actor and run identity;
- audit event;
- stable typed outcome;
- protection from duplicate model calls.

## 9. LLM Data Boundary

### 9.1 Prompt Construction

Prompts may contain:

- system policy;
- approved tool descriptions;
- sanitized incident metadata;
- sanitized tool results;
- approved integration documentation excerpts;
- synthetic examples.

Prompts must not contain restricted data.

### 9.2 Output Handling

Model output is:

- validated against a structured schema;
- checked for allowed classification and action values;
- rejected when it asks for forbidden data or tools;
- stored as a concise decision summary rather than private chain-of-thought;
- treated as a proposal until deterministic tools or humans confirm material actions.

### 9.3 Provider Controls

Provider selection must evaluate:

- data retention settings;
- training-use settings;
- regional or contractual requirements;
- authentication and key management;
- rate limits and cost controls;
- audit and deletion capabilities.

The portfolio baseline still prohibits raw financial data regardless of provider settings.

## 10. Prompt Injection Defense

Uploaded documents, integration metadata, issue text, repository files, and external API responses may contain malicious instructions.

Rules:

- file text is data, never a system instruction;
- tool permissions are defined outside model context;
- the model cannot create a new tool by naming it;
- tool arguments are validated independently;
- repository instructions from untrusted files cannot override `AGENTS.md` or sandbox policy;
- document content cannot request secrets, broader access, merge, or deployment;
- suspicious instructions are recorded as untrusted content and ignored;
- evaluation includes attempts to make the agent request forbidden data.

## 11. Structural File Profile Safety

The structural profiler may inspect raw files inside the deterministic processing boundary but produces only minimized metadata.

Allowed profile content:

- file format;
- encoding;
- delimiter;
- sheet names only when approved, otherwise hashes or normalized labels;
- visible and hidden sheet counts;
- row and column counts;
- header names or approved hashes;
- data type categories;
- reporting-year count;
- requested-year presence;
- warning codes;
- profile version.

Disallowed profile content:

- row samples containing amounts or identifiers;
- full cell values;
- formulas revealing customer data;
- embedded document content;
- comments or notes copied verbatim without sanitization.

## 12. Logging and Trace Redaction

Never log or trace:

- passwords;
- session cookies;
- service credentials;
- raw files;
- financial rows;
- personal identifiers;
- full authorization headers;
- database connection strings;
- unrestricted stack traces containing sensitive values.

Agent traces store:

- tool name;
- sanitized arguments;
- sanitized result summary;
- status and error code;
- timing;
- token and cost data;
- evidence and decision summary.

Redaction must be tested, not assumed.

## 13. Retry and Idempotency Security

The LLM cannot decide whether retry is safe.

Java determines retry eligibility from:

- idempotency policy;
- side-effect state;
- partial result cleanup;
- attempt count;
- current job status;
- integration-specific rules.

A retry request must:

- reauthenticate and reauthorize;
- verify incident and job state;
- use an idempotency key;
- reject stale or duplicate approval;
- record the actor and reason;
- not overwrite successful results silently.

## 14. Repair Sandbox Boundary

### 14.1 Required Isolation

Each repair run uses an ephemeral sandbox or container with:

- isolated repository clone;
- non-main branch;
- approved synthetic fixture;
- approved command wrappers;
- no production credentials;
- no production database access;
- no customer files;
- restricted filesystem paths;
- restricted or disabled external network access;
- time, CPU, memory, and output limits;
- cleanup or controlled retention.

### 14.2 Repository Access

The Repair Agent may read only files required by the ticket. Broad repository ingestion into the model is discouraged and should be bounded by search and focused reads.

### 14.3 Command Access

Provide typed tools for approved build and test commands. Do not expose a general interactive shell to the model.

### 14.4 Git Permissions

The agent may:

- create an isolated branch;
- apply and revert patches;
- create commits in the sandbox;
- create a draft pull request through a restricted provider.

The agent may not:

- write to `main`;
- modify branch protection;
- approve or merge its own change;
- deploy;
- access repository secrets.

## 15. Human Approval Boundaries

Human approval is required before:

- selecting authoritative behavior for a new integration variant;
- starting a repair run;
- accepting a change that affects financial or tax behavior;
- merging agent-generated code;
- deploying a fix;
- using any data outside the approved synthetic and sanitized boundary.

Approvals are persistent, attributed, scoped, and revocable.

## 16. Secrets Management

- no secrets in Git;
- provide safe `.env.example` values only;
- separate local, CI, and production credentials;
- rotate compromised credentials;
- do not put secrets in prompts, traces, tickets, screenshots, or pull requests;
- grant least privilege;
- use managed secret storage in the cloud milestone;
- prevent frontend bundles from containing backend secrets.

## 17. Document Storage Security

Version 0.1 local storage:

- server-generated storage keys;
- no client-supplied arbitrary paths;
- restricted storage root;
- company-scoped metadata authorization;
- content-type, extension, and size validation;
- checksum calculation;
- safe filename handling;
- no executable use of uploaded content.

Future S3 storage:

- private buckets or objects;
- tenant-aware key policy;
- short-lived pre-signed access where used;
- encryption and lifecycle configuration;
- no public listing;
- audit and retention controls.

## 18. Security Test Strategy

Minimum areas:

- session and CSRF behavior;
- password storage;
- tenant-isolation matrix;
- object identifier guessing;
- MCP service and tool authorization;
- mismatched company/incident scope;
- schema validation and oversized tool arguments;
- state-changing tool idempotency;
- forbidden tool requests;
- prompt injection attempts;
- trace redaction;
- sandbox path and command restrictions;
- attempts to write to `main`;
- attempts to request raw financial data;
- retry with stale or unsafe state;
- secret scanning in repository and CI artifacts.

## 19. Incident Response for Security Failures

A suspected security failure should:

1. stop the affected agent or processing path;
2. preserve sanitized audit evidence;
3. revoke or rotate credentials when needed;
4. prevent automatic retry when it could repeat exposure;
5. classify affected companies and data;
6. notify an authorized human;
7. create a security issue outside ordinary agent repair when appropriate;
8. verify containment before resuming.

The Repair Agent is not automatically authorized to fix security incidents.

## 20. Future Review Triggers

Security boundaries require explicit review when introducing:

- real customer data;
- a new LLM provider;
- external Jira or GitHub integration;
- S3 pre-signed uploads;
- Kafka events containing incident evidence;
- Redis-backed sessions;
- third-party API credentials;
- mobile or external clients;
- additional agents;
- Kubernetes or broader service mesh access;
- production use of generated code.
